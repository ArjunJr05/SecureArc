INTRODUCTION
Security in the cloud spans identity, network, data and governance at the same time, and a weakness in any one of these domains can negate strong controls in the others. This project applies the AWS Well-Architected Security Pillar to design and implement a secure and compliant AWS cloud architecture using defence-in-depth, covering IAM, Amazon VPC, AWS KMS, AWS CloudTrail and AWS Config. The security domains addressed by the project are introduced below.
AWS Security Architecture and Identity
Cloud workloads that process personal learner data are attractive targets, yet many security incidents originate from simple weaknesses: over-permissive identities, forgotten long-term access keys, publicly reachable storage and missing audit logs. Without a structured design approach, security controls are added piecemeal, overlap inconsistently and leave gaps between services. This project addresses the gap by applying the AWS Well-Architected Security Pillar to design a six-layer defence-in-depth architecture and by implementing AWS IAM roles, permission boundaries and multi-factor authentication so that every human and machine identity holds only the permissions it needs.
AWS Network Security
A flat network in which application servers and databases share the same exposure as the load balancer allows a single compromised host to reach every other resource. Traditional perimeter-only firewalls are not sufficient for cloud workloads that scale dynamically. This project solves the network challenge by building an Amazon VPC with public, private-application and isolated database subnets across two Availability Zones, chained security groups, network ACLs, VPC endpoints and VPC Flow Logs, so that only HTTPS traffic to the load balancer is reachable from the internet.
AWS Data Protection
Learner records, credentials and audit logs are sensitive, and unencrypted storage turns every backup, snapshot or misconfigured bucket into a potential data breach. Managing encryption keys manually is error-prone and difficult to audit. This project implements a customer managed AWS KMS key with automatic rotation and a key policy that separates key administrators from key users, and applies it to Amazon S3, Amazon RDS, Amazon EBS and CloudTrail logs, with TLS 1.2 or higher protecting data in transit.
AWS Governance, Logging and Compliance
Preventive controls cannot prove that they remain in place. Configuration drift, emergency changes and human error silently erode a secure baseline, and without audit logs an organisation cannot investigate or demonstrate compliance. This project activates a multi-Region AWS CloudTrail trail with log file validation, and uses AWS Config with CIS-aligned managed rules and automated remediation to continuously assess resources, identify non-compliant configurations, and document the risks found with their recommended remediation steps.

MODULE 1
SECURITY ARCHITECTURE AND IAM
4.1.1 PROCEDURE FOR SECURITY ARCHITECTURE AND IAM
The Security Architecture and Identity module forms the foundation of the entire secure cloud design. Before any network, encryption or monitoring control is configured, the security objectives, trust boundaries and identity model of the workload must be defined. This section documents how the AWS Well-Architected Security Pillar was used to design a defence-in-depth architecture, and how AWS Identity and Access Management (IAM) was configured to enforce least-privilege access for every human and machine identity.
Overview
The reference workload is a three-tier web application that processes personally identifiable learner data: an Application Load Balancer in public subnets, an application tier on Amazon EC2 in private subnets, and an encrypted Amazon RDS database in isolated subnets. Around this workload, six independent control layers were designed — governance, identity, network, compute, data and detection — so that the failure of any single control does not expose the data. All resources are deployed in the us-east-1 Region across two Availability Zones.

Step 1: Threat Modelling and Security Requirements
A lightweight STRIDE-based threat model was prepared for the reference workload. The assets considered were learner PII, application credentials, encryption keys and audit logs. The principal threats identified were credential theft, privilege escalation, public exposure of storage, unencrypted data, undetected configuration drift and tampering with audit logs. Each threat was linked to one or more preventive and detective controls, which form the requirements for the remaining modules.
Step 2: Defence-in-Depth Architecture Design
The architecture was designed in six concentric layers. An attacker must defeat every layer in turn to reach the data, and each layer generates evidence that is collected by the detection layer:
Governance: AWS Organizations service control policies (SCPs) prevent disabling CloudTrail, deleting Config recorders or leaving approved Regions.
Identity: IAM roles with temporary credentials, mandatory MFA and permission boundaries.
Network: VPC with public, private and isolated subnets, stateful security groups and stateless network ACLs.
Compute: IMDSv2 enforced on all instances, patched AMIs and access through AWS Systems Manager only.
Data: AWS KMS customer managed keys, S3 Block Public Access and encrypted RDS storage and backups.
Detection: CloudTrail, AWS Config and CloudWatch alarms for continuous visibility.
Step 3: AWS IAM – Least-Privilege Identity Control
IAM was configured so that no human user holds long-term access keys. The following identities and policies were created:
Root account: MFA enabled, no access keys, used only for account-recovery tasks.
SecureArchAdmin role: assumed through IAM Identity Center with MFA; permission boundary prevents IAM privilege escalation and prevents stopping CloudTrail.
SecureArchAppRole (instance profile): s3:GetObject and s3:PutObject only on the application data prefix, kms:Decrypt and kms:GenerateDataKey only on one CMK ARN, and logs:PutLogEvents for the application log group.
SecureArchAuditor role: read-only access (SecurityAudit managed policy) for reviewing CloudTrail and Config findings.
Account password policy: minimum 14 characters, complexity required, 90-day maximum age and reuse prevention of 24 passwords.

Step 4: Validation with IAM Access Analyzer
IAM Access Analyzer was enabled to detect resources shared outside the account, and the policy validation feature was used to check every custom policy for errors, security warnings and overly permissive statements. The IAM policy simulator was then used to confirm that the application role is allowed to perform only the intended actions and that all other actions are implicitly denied.
Step 5: Identity Monitoring and Credential Hygiene
To keep the identity layer trustworthy after deployment, CloudWatch metric filters and alarms were created on the CloudTrail log group for the events that signal identity abuse: use of the root account, console sign-in without MFA, changes to IAM policies, and creation of access keys. Each alarm publishes to an Amazon SNS topic so that the security owner is notified within minutes.
The IAM credential report was generated and reviewed to confirm that no user holds an unused password, an unrotated access key or a disabled MFA device. Because all human access is federated through IAM Identity Center, the report is expected to remain empty of long-term user credentials, and any deviation is treated as a finding.

Key Observations

MODULE 2
NETWORK SECURITY
4.2.1 PROCEDURE FOR NETWORK SECURITY
The Network Security module isolates the workload inside an Amazon Virtual Private Cloud (VPC) and controls every network path to and from it. This section documents how the VPC, subnets, route tables, security groups, network ACLs and VPC endpoints were designed and validated so that learner data is never reachable directly from the internet.
Overview
The network follows a three-tier segmentation pattern. Only the Application Load Balancer and the NAT gateway sit in public subnets. The application servers sit in private subnets with outbound-only internet access through the NAT gateway. The database sits in isolated subnets whose route tables contain no route to the internet at all. Traffic between tiers is permitted only by explicit security group references.

DATA PROTECTION
4.3.1 PROCEDURE FOR DATA PROTECTION
The Data Protection module ensures that all learner data is encrypted at rest and in transit using keys that the organisation controls. This section documents how AWS Key Management Service (AWS KMS) customer managed keys were created, governed and applied to Amazon S3, Amazon RDS, Amazon EBS and CloudTrail logs.
Overview
AWS KMS provides centralised creation, storage, rotation and auditing of cryptographic keys, with the key material protected in FIPS 140-validated hardware security modules. Instead of encrypting bulk data directly, services use envelope encryption: KMS generates a unique data key for each object or volume, the data is encrypted locally with that key, and the data key itself is stored only in encrypted form alongside the data. This design means the master key never leaves KMS.

Step 2: Key Policy and Separation of Duties
The key policy separates people who manage the key from the identities that use it. Key administrators can enable rotation, edit the policy and schedule deletion, but cannot encrypt or decrypt data. Key users, namely the application role and the CloudTrail and Config service principals, can use the key for cryptographic operations but cannot change it. Grants are used for AWS services such as RDS and EBS, and the kms:ViaService condition restricts use of the key to requests that arrive through the intended AWS services.
Step 3: Encrypting the Data Stores
Amazon S3: default encryption set to SSE-KMS with the CMK and S3 Bucket Keys enabled to reduce KMS request cost; a bucket policy denies any PutObject request that is not encrypted with aws:kms; S3 Block Public Access is enabled on all four settings.
Amazon RDS: storage encryption enabled with the CMK at creation, which also encrypts automated backups, snapshots and read replicas.
Amazon EBS: EBS encryption by default enabled for the Region using the CMK so that every new volume is encrypted.
CloudTrail logs: log files are encrypted with the CMK, as described in Module 4.
Step 4: Encryption in Transit
An AWS Certificate Manager (ACM) public certificate was attached to the HTTPS listener of the load balancer with a TLS 1.2 minimum security policy and automatic HTTP-to-HTTPS redirection. The RDS instance requires SSL connections through the rds.force_ssl parameter, and all calls to AWS APIs use TLS through the VPC endpoints.
Step 5: Verification
Verification was carried out by uploading a test object, confirming in the object properties that it reports SSE-KMS with the expected key ARN, and then removing the application role from the key policy to confirm that the object can no longer be read. CloudTrail events for kms:Decrypt and kms:GenerateDataKey were located to prove that every cryptographic operation is audited.

MODULE 4
CLOUDTRAIL, AWS CONFIG AND RISK REMEDIATION
4.4.1 PROCEDURE FOR CLOUDTRAIL, AWS CONFIG AND RISK REMEDIATION
The Logging, Compliance and Risk Remediation module provides the detective and corrective controls of the architecture. AWS CloudTrail records who did what and when, AWS Config records what every resource looks like and whether it complies with the required baseline, and a documented risk register records the weaknesses found together with their remediation. This section documents how these controls were configured and used.
Overview
Preventive controls reduce the likelihood of an incident, but they cannot prove that they are still in place. CloudTrail and AWS Config close this gap by producing continuous, tamper-evident evidence. CloudTrail answers the question of who performed an action, while AWS Config answers whether the resulting configuration is compliant, and the two are correlated during investigations.
Step 1: AWS CloudTrail – Activity Logging
Trail: secure-arch-trail created as a multi-Region organisation-wide trail that records management events for read and write operations, and S3 data events for the learner-data bucket.
Storage: logs delivered to a dedicated, versioned S3 bucket with Block Public Access, a bucket policy that allows only the CloudTrail service principal to write, and SSE-KMS encryption using the CMK from Module 3.
Integrity: log file validation enabled so that a SHA-256 digest file proves logs have not been altered or deleted.
Real-time alerting: the trail also streams to CloudWatch Logs. Metric filters and alarms notify the security team through Amazon SNS on root account usage, console login without MFA, IAM policy changes, security group changes, KMS key deletion scheduling and any StopLogging call.

Step 4: Automated Remediation and Re-Assessment
For the most critical findings, AWS Config remediation actions were attached to the rules using AWS Systems Manager Automation documents. For example, a public S3 bucket is automatically reconfigured with Block Public Access enabled, and a security group that opens SSH to the world has the offending rule revoked. After remediation the rules are re-evaluated, and the compliance dashboard returns to COMPLIANT. All remediation actions are themselves recorded by CloudTrail, which preserves the evidence chain.

Key Observations
The detective layer closes the loop on the whole architecture. Preventive controls from Modules 1 to 3 are only valuable if their continued presence can be proven, and CloudTrail together with AWS Config provides that proof continuously rather than only at audit time.
Complete activity record: The multi-Region trail captures management and data events from every Region, including actions taken by the administrator role and by AWS services.
Tamper-evident evidence: Log file validation, a versioned encrypted log bucket and service control policies make it difficult to alter or delete audit records without detection.
Continuous compliance: AWS Config evaluated twelve managed rules against all recorded resources, and the dashboard returned to COMPLIANT after remediation.
Faster response: CloudWatch alarms and SNS notifications reduced the time between a risky change and the security owner being informed to a few minutes.
Together, these observations show that the six-layer design satisfies the objectives of the Well-Architected Security Pillar: identities are controlled, data is protected, activity is traceable and deviations are detected and corrected automatically.
CONCLUSION
The secure and compliant cloud architecture demonstrates how the AWS Well-Architected Security Pillar can be turned into a concrete, verifiable design. A defence-in-depth model was built from six independent layers. AWS IAM roles, permission boundaries and multi-factor authentication provide least-privilege identity control; an Amazon VPC with public, private and isolated subnets, chained security groups and network ACLs removes direct exposure of the application and database tiers; and AWS KMS customer managed keys encrypt data at rest in Amazon S3, RDS, EBS and the audit logs, while TLS protects data in transit.
Detective and corrective controls complete the architecture. AWS CloudTrail records every API action in an encrypted and tamper-evident log, and AWS Config continuously evaluates resources against CIS-aligned rules, with automated remediation restoring compliant settings. A documented risk register captured the weaknesses discovered together with their severity and recommended remediation. Overall, the project shows that a secure, auditable and compliant environment can be built entirely with managed AWS services and repeated reliably through automation.
Future Scope
Several enhancements are identified. Amazon GuardDuty, AWS Security Hub and Amazon Inspector can be added for threat detection, centralised findings and vulnerability scanning. AWS WAF and AWS Shield can protect the load balancer from application-layer and DDoS attacks. The whole architecture can be expressed as infrastructure as code with AWS CloudFormation or Terraform and checked in a CI/CD pipeline, so that insecure changes are rejected before deployment. Multi-account governance with AWS Control Tower, Amazon Macie for discovering sensitive data in S3, and automated incident-response runbooks would further strengthen the posture for enterprise deployment.
System Impact and Real-World Relevance
Many real-world breaches are caused by configuration errors rather than sophisticated attacks. By embedding least privilege, network isolation, encryption and continuous compliance checking from the first design decision, the architecture reduces the likelihood and impact of such incidents. It also produces the audit evidence needed by regulations and frameworks such as ISO 27001, SOC 2, GDPR and the CIS Benchmarks, which lowers the cost and effort of audits for educational institutions and other organisations handling personal data.
Engineering Trade-offs and Design Decisions
Strong security introduces trade-offs. Private subnets with NAT gateways and interface endpoints increase monthly cost compared with a flat public network. Customer managed KMS keys add key-management responsibility and KMS request charges, which are reduced by using S3 Bucket Keys. Continuous AWS Config recording and CloudTrail data events increase storage and evaluation cost and were therefore limited to the resources that hold learner data. Strict least-privilege policies require more design effort and testing, which was addressed using IAM Access Analyzer and the policy simulator. These decisions favour security and auditability while keeping the architecture practical to operate.
Limitations of the Current System
The architecture was validated on a reference workload and a deliberately weakened test configuration, and it may not cover every service or workload pattern used in production. AWS Config managed rules check configuration state but do not detect application-level vulnerabilities or runtime threats. Automated remediation can disrupt workloads if rules are too aggressive and must be tested carefully. Finally, a single-account deployment was used, and an enterprise environment would require multi-account separation and centralised logging.
